# RAG against the machine

## Description

This project implements a Retrieval-Augmented Generation (RAG) pipeline for answering questions about a large codebase. The system ingests a repository, indexes it into searchable chunks, retrieves the most relevant snippets for a question, and uses a local language model to answer in a grounded way.

The target corpus for this project is the vLLM repository shipped with the assignment. The goal is to locate the relevant source files and character ranges, rank them by relevance, and generate answers that stay grounded in the retrieved evidence instead of relying on model memory alone.

The system is built to satisfy the assignment requirements described in the project PDF and follows the expected CLI workflow used during evaluation.

## System architecture

The project follows a classic four-stage RAG design:

1. Indexing
   - Reads source files from `data/raw/vllm-0.10.1`
   - Splits files into chunks according to file type
   - Stores chunk metadata such as file path and character offsets
   - Persists the index under `data/processed/`

2. Retrieval
   - Uses BM25-style lexical search for fast matching over indexed text
   - Uses a semantic embedding index (via ChromaDB + SentenceTransformers) for similarity-based retrieval
   - Combines both result sets with reciprocal rank fusion (RRF) to get a more robust ranking

3. Answer generation
   - Retrieves the top-k relevant chunks
   - Injects them into the prompt as evidence
   - Calls the local model to answer while constraining the response to the retrieved context

4. Evaluation
   - Compares retrieved sources with a ground-truth dataset using recall@k
   - Validates that the retrieved file and overlapping character range match the expected source region

The main orchestration is handled in `src/__main__.py`, while chunking, lexical retrieval, semantic retrieval, and evaluation are separated into dedicated modules.

## Chunking strategy

The project implements file-aware chunking to handle different source types appropriately:

- Python files are chunked using a Python-aware splitter from LangChain
- Markdown and text files are chunked using a Markdown/text splitter
- The default chunk size is `2000` characters
- Overlap is kept small to preserve local context while preventing excessive noise

Each chunk stores:

- `file_path`
- `content`
- `first_character_index`
- `last_character_index`

This is essential because the evaluator compares both the file path and the overlapping character range, so the chunk metadata must remain accurate and stable.

## Retrieval method

The retrieval layer uses a hybrid approach:

- Lexical retrieval: BM25 via `bm25s`
- Semantic retrieval: embeddings generated by `sentence-transformers/all-MiniLM-L6-v2` and indexed in ChromaDB
- Ranking fusion: reciprocal rank fusion (RRF) combines both result lists into a single ranked candidate set

This hybrid method helps bridge the gap between keyword matching and semantic similarity. A question may use different wording than the code it refers to, and this combination makes it more likely that the right source location is recovered.

## Design decisions

Several implementation choices were made to align the project with the assignment and the evaluator:

- File-path precision is treated as critical, since the evaluator compares source locations verbatim
- Chunk metadata uses character offsets, which makes it possible to evaluate approximate overlap instead of exact-span equality
- Retrieval is configurable through CLI arguments to support both debugging and automated grading
- Output matches the required pydantic models and JSON schema expected by the evaluator
- The system is designed to fail gracefully for empty queries, invalid inputs, missing files, and malformed JSON

## Challenges faced

The most important difficulties in this project were related to retrieval quality and data correctness:

- The same concept may be described using very different vocabulary in the source code and in a user question
- A repository contains many noisy or semantically weak chunks, so ranking quality matters a lot
- Source spans must be returned with exact file paths and approximate ranges; a small mismatch can invalidate a retrieval result
- Long context windows and chunk size constraints must be respected because the project rejects overlong sources

To mitigate these issues, the project uses hybrid retrieval, chunk metadata tracking, and careful output validation. This makes it easier to balance recall, precision, and robustness in a real RAG workflow.

## Performance analysis

The project is designed around the evaluation requirements in the assignment:

- Indexing must complete within 5 minutes for the full corpus
- Retrieval should remain fast enough for dataset-wide runs
- Recall@k is the main metric used for judging retrieval quality
- The expected thresholds are:
  - Docs questions: at least 80% recall@5
  - Code questions: at least 50% recall@5

The evaluator computes recall by checking whether at least one retrieved source overlaps a correct answer source in the same file, with a low overlap threshold. This means the system does not need an exact match to succeed; it only needs to retrieve a relevant region of the right file.

## Instructions

### Installation

From the repository root:

```bash
uv sync
```

### Index the corpus

```bash
uv run python -m src index --max_chunk_size 2000
```

This builds the searchable index under `data/processed/`.

### Search a single query

```bash
uv run python -m src search "How does the OpenAI server work?" --k 5
```

### Search an entire dataset

```bash
uv run python -m src search_dataset \
  --dataset_path data/datasets/UnansweredQuestions/dataset_docs_public.json \
  --k 10 \
  --save_directory data/output/search_results/UnansweredQuestions
```

### Generate answers from search results

```bash
uv run python -m src answer_dataset \
  --student_search_results_path data/output/search_results/UnansweredQuestions/dataset_docs_public.json \
  --save_directory data/output/search_results_and_answer/UnansweredQuestions
```

### Run local evaluation

```bash
uv run python -m src evaluate \
  --student_search_results_path data/output/search_results/UnansweredQuestions/dataset_docs_public.json \
  --dataset_path data/datasets/AnsweredQuestions/dataset_docs_public.json
```

### Full evaluation workflow

The project follows the reference flow used during the defense:

```bash
uv run python -m src index --max_chunk_size 2000
uv run python -m src search_dataset \
  --dataset_path data/datasets/UnansweredQuestions/dataset_docs_public.json \
  --k 10 \
  --save_directory data/output/search_results/UnansweredQuestions
./moulinette evaluate_student_search_results \
  data/output/search_results/UnansweredQuestions/dataset_docs_public.json \
  data/datasets/AnsweredQuestions/dataset_docs_public.json \
  --k 10 --max_context_length 2000
uv run python -m src answer_dataset \
  --student_search_results_path data/output/search_results/UnansweredQuestions/dataset_docs_public.json \
  --save_directory data/output/search_results_and_answer/UnansweredQuestions
```

## Example usage

```bash
# build the chunked index
uv run python -m src index --max_chunk_size 2000

# ask a single question
uv run python -m src search "What is the purpose of the tokenizer in vLLM?" --k 3

# answer a question using the retrieved context
uv run python -m src answer "How do I configure the OpenAI-compatible server?" --k 5
```
